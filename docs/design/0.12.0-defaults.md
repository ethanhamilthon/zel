# 0.12.0: defaults in Lua — design spec

Zel stops giving the agent host functions. The agent VM has the Lua standard
library only. Everything else (`sh`, `read`, `edit`, ...) is plain Lua in
`~/.config/zel/defaults/`, wired in through `functions` of the config. Lua
talks to Zel through the `zel` CLI (`zel exec`, `zel steer`, `zel status`,
`zel choice`, `zel print`, `zel session`, `zel rename`).

## 1. Config files

- `zel` loads config files in order. Default list: `~/.config/zel/init.lua`
  (or `$ZEL_HOME/init.lua`), then `./zel.lua` of the start folder. Both are
  optional: a missing default file is skipped silently.
- `--config FILE` (repeatable) appends files after the defaults; a missing
  `--config` file is an error. `--no-default-configs` drops the two defaults.
  `~` is expanded by zel; relative paths are from the start folder.
- Merge: later files win for `systems`, `prompts`, `functions`, `commands`
  (by name) and `settings` keys; a replacement adds a warning
  (`b.lua: functions.read replaces a definition from init.lua`). `hooks`
  append in file order. `loads` stay (relative to their file, not nested).
- Every entry keeps its source file (for the Config screen).
- `connect.json` stays as it is.
- No file watching. Config is read at start, on new session, on resume and on
  Ctrl+R in the Config screen. A reload during a turn applies after the turn.
  On a failed reload the old config stays; the error shows in Config.
  `config_changed` hooks run after every reload.
- `zel -p` children: `ZEL_CONFIGS` = the explicit `--config` files (absolute,
  joined with `\n`), `ZEL_NO_DEFAULT_CONFIGS=1` when the parent had the flag.
  A child resolves the default files itself (its own `zel.lua` with `--cwd`).
- First run (`EnsureHome`): creates `init.lua` (the default one, see 3.3) if
  missing, `defaults/` if missing, `connect.json`, `.gitignore`. Existing
  files are never touched. `zel defaults --reset` rewrites `defaults/` from
  the binary (removes the folder first). The folder is the user's afterwards.

Top-level keys of a config table: `settings`, `systems`, `prompts`,
`functions`, `hooks`, `commands`, `loads`. Unknown key = error.

```lua
functions = {
  read = d.read,                                  -- an entry from defaults
  server_sh = { description = "`server_sh(cmd) -> {ok, code, out}` - bash on mainserver",
                fn = function(cmd) ... end },
},
commands = {
  { name = "Commit", description = "commit the diff", key = "alt+g", fn = function() ... end },
},
```

- A function entry is a table `{description = string, fn = function}`; the
  `description` is the whole line in the prompt (signature included). No
  other fields. Mode differences are the config's business
  (`os.getenv("ZEL_MODE")`).
- A command is `{name, description?, key?, fn}`; `commands` is a list (menu
  order). `key` uses the format of `settings.keys` (`ctrl+x`, `alt+x`); a
  clash with `settings.keys` or another command is a config error.

## 2. VMs

- Config VM: runs the config files and sync hooks, owns the original
  closures. Separate from the session VM.
- Session VM (the `lua` tool): Lua 5.1 stdlib, plus the `functions` of the
  config as globals. When the VM is created, all `fn`s are copied from the
  config VM in ONE copier pass (`copy.go`), so upvalues shared between
  functions stay shared in the copy (e.g. the `cwd` of defaults). Copy errors
  (userdata upvalue, ...) are config errors at load time.
- No host API at all: no `print`, `sh`, `read`, `task.*`, `choice`, `cd`,
  `docs`, `models`, `session`, no `require("zel")`.
- The result of a call: the values of `return ...`; when the last statement
  is a function call, its values (the code is rewritten so the call is
  returned); when the whole code is an expression, its value. Rendering as in
  0.11: strings as they are, tables as JSON, several values one per line, nil
  results give no line. A raised error appends `error: <msg>`.
- Nothing a VM does may reach Zel's terminal: no `print`; `io.write`,
  `io.stdout`, `io.stderr` go to a discarded sink; children of
  `io.popen`/`os.execute` get no TTY: stdin `/dev/null` (popen "r"), stderr
  to `/dev/null`, `os.execute` stdout to `/dev/null`.
- `io.popen` and `os.execute` are hardened in Go (the only Go change to the
  stdlib): child in its own process group, cwd = the session start folder,
  env = the session environment (`ZEL_*` + `settings.env`), the whole group
  killed when the VM context ends (call timeout, Ctrl+D, reset, session end).
- Call timeout (`settings.timeout`), output cut (`settings.output`, saved to
  `outputs/b<N>.txt`), VM reset on timeout/reload/session change: as 0.11.
- `package.path` of every VM starts with `<home>/defaults/?.lua;
  <home>/defaults/?/init.lua`, then the folder of each config file.
- Async hooks and commands run in a fresh VM with a copied `fn` (as async
  hooks in 0.11). A command has no timeout; a returned nonempty string is
  shown like `zel print`; an error is a red line in the chat.
- Removed: background tasks (registry, `task.*`, task lines, task
  notifications). Background work = `sh("cmd > log 2>&1 &")` + `zel status
  new` + `zel steer`.

## 3. defaults (Lua, embedded, written to `<home>/defaults/`)

### 3.1 Module

`require("defaults")` returns a table of entries. Each entry is
`{description, fn}` with a metatable `__call = function(self, ...) return
self.fn(...) end`, so `d.sh("git status")` works in hooks and commands, and
`functions = {sh = d.sh}` installs `fn`. Helpers are `local`. Errors are
raised as `"fn: CODE: msg"` with level 0; codes `EINVAL ENOENT ENOMATCH
EAMBIG ELIMIT EFAIL EDENIED ETIMEOUT ECANCELED`. Paths are relative to the
defaults' `cwd` (initially the session start folder), `~` is expanded. Every
entry that does something visible first runs `zel status "<text>"`
(`read <path>`, `write <path>`, `edit <path>`, `grep <re>`,
`$ <first line of cmd>`); a failing `zel status` is ignored.

### 3.2 Entries

- `sh(cmd, {timeout, cwd, env, stdin, check}?) -> {ok, code, out, timed_out, ms}`:
  runs `zel exec --timeout N --cwd D [--env K=V]... -- bash -c CMD` with
  stdin, parses its JSON. `check` raises EFAIL on code ~= 0.
- `read(path) -> text`; png/jpg/jpeg/gif/webp: `zel steer --file PATH` (the
  image goes to the next request) and returns nil. > 16 MiB: ELIMIT.
- `write(path, s, {append}?)` creates parent folders.
- `edit(path, old, new, {all}?) -> n`, `edit(path, {{old, new, all?}, ...}) -> n`:
  exact text, ENOMATCH, EAMBIG unless all; several edits all or nothing.
  The descriptions carry the 0.11 advice ("change existing files with
  `edit`; write large files in small chunks").
- `slice(s, from, count?)`, `list(dir?) -> {name, dir, size}[]`,
  `glob(pattern) -> paths` (`**` supported), `grep(re, {path, glob, fixed, max}?)
  -> {file, line, text}[]` (max 200), `exists(path) -> bool, "file"|"dir"|nil`.
  `glob`/`grep`/`list` use `rg` when it is on PATH (respects .gitignore),
  else `find`/`grep -rnE`. Must work on macOS and Linux.
- `cd(dir?)`: the folder of the next calls; no argument = the start folder.
- `choice(question, {options...}) -> id`: `zel choice`, does not block.
- `docs(topic?) -> text` (`zel docs`), `models() -> list` (`zel models
  --json`), `session() -> table` (`zel session --json`), `rename(name)`.

### 3.3 The default init.lua

Requires defaults and lists every entry in `functions` (`choice` only when
`ZEL_MODE ~= "headless"`), plus the commented settings example of 0.11.

## 4. Prompt

- Tool description: `internal/core/prompt/lua_tool.md` (`{timeout}`
  replaced). Nothing else.
- System prompt = `internal/core/prompt/zel.md` (static, about Zel and its
  CLI), then `## Functions` with one line per function sorted by name
  (`` `name` - description ``, or just the description when it already
  starts with a backtick), then the `systems` of the configs in file order.
  Built at new session, resume and reload; stored in the history as now.
- `lua_main.md` and the `[main]/[headless]/[nest]` markers are removed.

## 5. CLI and socket

All commands act on `$ZEL_SESSION_ID`; `-s ID` picks another live session
(socket `ipc.Path(<store>/run, ID)`, the token is read from a 0600 file in
the session folder). Without a session: exit 1 with a clear message. Exit
codes as `exitCodes` in `core/socket.go`.

- `zel exec [--timeout S] [--cwd DIR] [--env K=V]... -- CMD ARGS...`: no
  socket. Runs CMD in a new process group, stdin passed through, stdout and
  stderr merged; prints `{"ok","code","out","timed_out","ms"}` JSON. On
  timeout kills the group. After CMD exits it waits at most 100 ms for the
  pipes (a background `&` job keeps running and does not block it).
- `zel steer [-s ID] [--file PATH]... [TEXT|-]`: TEXT (or stdin) and images
  as a steering input. During a turn it is added after the tool results; when
  the session is idle it starts a new turn (like a notification).
- `zel status [-s ID] TEXT`: the text of the working line of the running
  call (cleared when the call ends). `zel status new TEXT` prints an ID: an
  own indicator line with its own timer. `zel status -i ID TEXT` updates it,
  `zel status -i ID --done` removes it. It lives until `--done` or until zel
  quits.
- `zel choice [-s ID] QUESTION OPTION...`: as 0.11 `choice()`: shows the
  picker, prints the ID, does not wait; the answer arrives as a notification.
  Headless: exit 6 (EDENIED).
- `zel print [-s ID] TEXT|-`: a dark gray line in the chat. Kept in the
  session history (shown on resume) but never sent to the model; Tracing
  shows it.
- `zel session [-s ID] --json`: `{id, name, cwd, root, mode, modes, depth,
  model, effort, provider}`.
- `zel rename [-s ID] NAME`.
- `zel defaults --reset`.
- `zel -p`, `zel docs`, `zel models [--json]`, `zel config`, `zel update`,
  `zel version`, `zel help` stay. `zel config` lists every file read.

## 6. UI

- Working line: elapsed · the `zel status` text of the running call (else
  the code's first line when `show_code`) · calls · queued input.
- Each `zel status new` indicator is a line above the working line:
  `◐ 6s · text` (the 0.11 task line style).
- `zel print` lines: `dark_gray`, no header.
- Menu: new item `Config`: read-only screen with Files, Systems, Functions,
  Prompts, Hooks, Commands (each with its source file; functions with the
  first line of the description; commands with their key) and the
  warnings/errors. Ctrl+R there reloads the config and shows the result.
- Menu lists the config `commands` (with their key hint); Enter runs one.
  Command keys work wherever the global keys work.
- Bug: the menu closes with `keys.menu`, not a hard-coded Ctrl+K.

## 7. Go contracts

```go
// config
type Paths struct {
    Files   []string // in load order: defaults (if kept) then --config files
    Connect string
}
func DefaultPaths(home, cwd string, configs []string, noDefaults bool) Paths
type System   struct{ Name, Text, Source string }
type Function struct{ Name, Description, Source string }
type Hook     struct{ Events []string; Async bool; Ref int; Source string }
type Command  struct{ Name, Description, Key, Source string; Ref int }
type Config struct {
    Paths            Paths
    Settings         Settings
    Systems          []System
    Prompts          map[string]string
    PromptSources    map[string]string
    Hooks            []Hook
    Functions        []Function
    Commands         []Command
    Files            []string // every file read, loads included
    Warnings, Errors []string
}

// core (the Controller exposes these to the TUI)
func (c *Controller) Config() *config.Config        // the current snapshot, nil before load
func (c *Controller) Reload()                       // exists; now also called from the Config screen
func (c *Controller) RunCommand(name string) error  // async; output/errors as records
type Indicator struct{ ID, Text string; Started time.Time }
func (c *Controller) Indicators() []Indicator       // zel status new, creation order
func (c *Controller) CallStatus() string            // zel status text of the running call, "" none
// Record kind "print": zel print lines and command output
```

`luart.Env` shrinks to what the VMs still need (session info for cwd/env,
`Log`). `ActiveTasks`, `TaskInfo`, `Tasks` go away.

## 8. Workstreams (parallel branches, integration later)

Each branch passes `make test` on its own. When your change breaks code
outside your files, make the smallest compiling adaptation (or a stub in a
file named `*_stub_<letter>.go`) and list it in the final report. Do not
touch `~/.config/zel`, `~/.local/bin/zel` or `~/.zel`; test with a temporary
`ZEL_HOME`/`HOME` and a binary built into a temp folder.

- **A — luart + config + core (VM, config, prompt)**: sections 1, 2, 4 and
  the `Config`/`Reload`/`RunCommand` part of 7: multi-file loading and
  flags (`--config` repeatable, `--no-default-configs` in `cli/run.go`),
  sources, `commands` parsing and key validation, `ZEL_CONFIGS`, no Watch,
  `EnsureHome` (takes the defaults files from `internal/defaults`, see C; stub
  until merged), session VM without host API, function copy, result rule,
  hardened popen/os.execute, terminal sink, `package.path`, async
  hooks/commands, removal of tasks, prompt assembly from
  `internal/core/prompt/*.md`. Tests in `luart` and `config`.
