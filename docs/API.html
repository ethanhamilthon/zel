Run make install to install ~/.local/bin/zel. First launch opens onboarding inside the application: provider name, base URL, API key, API type (responses or chat), then model and effort. Tab / Shift+Tab switch steps; Left / Right edit text; Enter advances. There is no setup subcommand.

Providers, keys, preferences, defaults, sessions, and tasks live in ~/.zel/zel.db. Keys are stored locally, not encrypted. Override the state directory with ZEL_HOME. Zel does not load or migrate old Dashy data. Manage preferences in Settings and providers in Providers. Model-list failures can be retried or bypassed through manual entry.

Headless mode prints the persisted session ID first, then the final answer and exits. Diagnostics use stderr. Model, provider and effort flags override defaults for this session only. Read committed history with zel session -s ID while running or after exit.

ZEL.md

---
name: My project
description: A short project description
color: terracotta
hooks:
  app_start: "./start.sh"
---
Your project system prompt.

Load $ZEL_HOME/ZEL.md, every ZEL.md from the filesystem root down to the working directory, then the optional --config FILE. The explicit file must exist. Markdown bodies and hooks accumulate in order; later metadata overrides earlier values. A session stores its prompt until Reload or New session. Reload during a turn defers prompt replacement until that turn ends.

One accent is used throughout the UI, with neutral shades and red for errors. The default is terracotta. Available colors:

terracotta, rose, dusty-pink, mauve, lavender, violet, slate, blue, sky, teal, sage, olive, moss, sand, ochre, amber, peach, clay, copper, plum

Lifecycle hooks

Each event maps to a shell command or list of commands, run relative to the defining file. Commands run in layer order with a 10-second timeout each. They receive ZEL_EVENT, session ID, context token count, current model selection, working directory, mode, and relevant event-specific data. See README for the exact environment contract.

app_start, app_exit
session_start, session_close
first_message, user_message
turn_start, turn_end
bash_start, bash_end
model_request_start, model_request_end
error

first_message fires once for the whole session. Session closing hooks run when switching sessions or quitting; application hooks run once per application lifecycle. Successful nonempty stdout is added to model context at the next safe request boundary. Pre-request hooks finish before the request. Output remaining after a turn waits for the next user message: it never starts a turn by itself. Closing output, errors, and stderr are visible only in Tracing. Shutdown waits for closing hooks within their timeouts.

Bash and hooks share the same head/tail output budget. A 4096-byte limit retains the first 2048 bytes, a truncation marker, and the last 2048 bytes. The marker is additional to the retained bytes. Zero means unlimited; the default is 8192 bytes. Hook stderr uses the same limit.

Ctrl+M and Ctrl+I require Kitty keyboard protocol support; otherwise use Menu. Chat contains only user messages, answers, and the working indicator. Tracing shows everything else. Search accepts :user text, :bash text, and all displayed entry types.

Files includes hidden entries, ., and .., with directories first. Enter opens a directory or edits a regular file using the UI editor preference, then VISUAL / EDITOR, defaulting to nvim. The editor hands the terminal back when it exits. Info shows project name, description, color, instruction layers, and token usage.

Security

Commands and hooks run with your user permissions and network access, not in a sandbox. Review unfamiliar project instructions and hooks before launching. API keys may reference environment variables with {{$VARIABLE}}. The full conversation and provider secrets are not explicitly passed to hooks; commands still inherit your shell environment.
